# Довідка програміста — Wall Protocol 1.2

## Архітектура

`obj_game` тепер зберігає лише стан походу: ефір, HP ядра, хвилю, вибір майданчика, результат, час і маршрут. Він не малює поле, не пересуває ворогів і не керує атаками веж.

| Ресурс | Відповідальність |
| --- | --- |
| `obj_app` | Постійний сервіс: клавіатура меню, повідомлення, автозбереження |
| `obj_audio` | Постійний музичний голос, обмеження частоти повторюваних SFX |
| `obj_splash`, `obj_menu`, `obj_text` | Відповідні екрани |
| `obj_button` | Самостійна кнопка: геометрія, hover, дія, стан доступності |
| `obj_game` | Стан походу та єдиний крок часу симуляції |
| `obj_wave` | Черга ворогів, інтервал появи, завершення хвилі; `banner_t` — таймер банера початку хвилі |
| `obj_board`, `obj_hud` | Лише відображення землі/дороги та інтерфейсу |
| `obj_path_node` | Редагована точка маршруту; невидима під час гри |
| `obj_build_pad` | Основа, вибір і посилання на конкретну вежу |
| `obj_tower` + 3 нащадки | Пошук цілі за `target_mode` (0 перший, 1 останній, 2 найсильніший, 3 найближчий), перезарядження, запуск снаряду |
| `obj_enemy` + 4 нащадки | Рух, HP, сповільнення, прорив |
| `obj_projectile` | Політ і застосування одиночної/AoE/крижаної атаки |
| `obj_effect` | Короткочасні ефекти: `fx_kind` 0 — іскри, 1 — кільце, 2 — спливаючий текст (`fx_text`) |
| `obj_core`, `obj_portal` | Об'єкти кінця й початку шляху |
| `obj_decor` + 5 нащадків | Дерева, камені, жаровні, стіни, надгробки |
| `obj_test` | Лише явний запуск із параметром `--wp-test` |
| `obj_sandbox` | Налаштування й панель ручного тестування в `rm_test` |

## Скрипти

- `scr_config`: бренд Eclipse Wire, палітра, каталог веж, хвилі, локалізація, запасний маршрут.
- `scr_world`: запуск кімнати, будівництво/продаж/покращення, damage, результат походу.
- `scr_ui`: спільне малювання UI, підписи, дії кнопок і діалоги; допоміжні `wp_text_a` (текст із прозорістю), `wp_clock`, `wp_star`/`wp_stars` (зірки з трикутників, без гліфів шрифту).
- `scr_save`: перевірка схеми, settings, JSON-запис, резервна копія, snapshot/restore.
- `scr_audio`: SFX і зміна гучності.
- `scr_layout`: лише запасні координати кнопок, якщо конкретна пара `page + action` відсутня.
- `scr_sandbox`: ручні тестові дії, прив'язка стартових ворогів до маршруту та fallback кнопок полігона.

## Тестова кімната `rm_test`

Вхід: кнопка **«Тестова кімната [F2]»** у головному меню або F2. Кімната відкривається на паузі, щоб встигнути оглянути розстановку. Натисніть «Продовжити» або Esc.

У Room Editor уже розставлені 6 вузлів маршруту, 6 основ, 3 типи веж на рівнях 1/2/3, 4 типи ворогів, портал, ядро та кнопки. Усі ці екземпляри можна переміщувати й налаштовувати. Стартові вороги прив'язуються до найближчого відрізка маршруту; їхній прогрес одразу відповідає позиції, тому вежі коректно вибирають ціль.

В екземпляра `obj_sandbox` доступні Variable Definitions:

| Поле | Початкове значення | Призначення |
| --- | --- | --- |
| `starting_aether` | 5000 | Ефір для експериментів із будівництвом |
| `test_wave` | 4 | Склад і складність тестової хвилі, від 1 до 8 |
| `invulnerable` | 1 | Безсмертя ядра; 0 повертає звичайну шкоду |

Нижня панель дозволяє породити кожен тип ворога або групу з 12, прибрати ворогів і снаряди, додати ефір, відновити ядро, перемкнути безсмертя, вибрати хвилю, викликати екрани перемоги/поразки, скинути кімнату та повернутися до меню. Після вибору хвилі натисніть звичайну кнопку початку хвилі або Пробіл; під час активної хвилі її номер не змінюється. Ручні вороги самі по собі не завершують похід. «Скинути кімнату» й «Спробувати знову» відновлюють її редакторську розстановку.

Полігон не записує й не видаляє збереження основного походу, включно з автозбереженням, виходом і результатами. Для завантаження походу поверніться в головне меню. Налаштування мови, звуку та вікна залишаються спільними.

Якщо видалені всі стартові вежі або всі вороги, fallback відновлює приклади. Для порожнього бойового поля під час тесту натисніть «Прибрати ворогів». Наявні вежі й кнопки не дублюються. Запасна розстановка кнопок полігона — `wp_sandbox_buttons()` у `scr_sandbox`; після навмисного видалення кнопки оновіть і цей список. Одноразовий `tools/add_test_room.py` повторно не запускайте: він має захист від перезапису `rm_test`.

## Робота в редакторі кімнат

### Маршрут

Відкрийте `rm_game` і переміщуйте маркери `obj_path_node`. У Variable Definitions задавайте `node_order` — унікальний номер, порядок проходження. Номери можна пропускати. Дорога малюється безпосередньо за позиціями цих екземплярів. Слідкуйте, щоб перший вузол був біля порталу, останній — біля ядра.

Не накладайте кілька вузлів з однаковим `node_order`. Самі маркери приховуються в runtime. Якщо залишилося менше двох вузлів, bootstrap відновить стандартний маршрут.

### Будівництво

`obj_build_pad` можна вільно переміщувати та додавати. Кожному новому майданчику задайте унікальний `pad_key`, наприклад `north_01`. Цей ключ пов'язує вежу зі збереженням. Якщо жодного майданчика немає, відновлюються 12 запасних.

Вежі `obj_tower_archer`, `obj_tower_rune`, `obj_tower_frost` теж можна поставити вручну. Під час запуску вони прив'язуються до найближчої вільної основи в межах 50 px; за відсутності такої основи створюється основа під вежею. `level` задає стартовий рівень 1–3.

Вороги породжуються `obj_wave` з окремих об'єктів. Для нового типу змінюйте каталог, нащадка та склад хвиль, а не малювання контролера.

### Кнопки

Кнопки меню та HUD — справжні екземпляри `obj_button`. Координати кімнати використовуються напряму. Поля:

- `action`: дія, наприклад `new`, `continue`, `options`, `wave`, `build0`;
- `page`: сторінка, на якій кнопка видима: `main`, `game`, `pause`, `options`, `language`, `result`;
- `button_w`, `button_h`: розмір;
- `nav_order`: порядок Tab/стрілок.

У редакторі кнопки різних сторінок можуть стояти одна поверх одної; це очікувано. Якщо навмисно видаляєте стандартну дію, видаліть її і з відповідного fallback-масиву `scr_layout`, інакше вона буде відновлена. Наявні кнопки bootstrap не переставляє.

### Декорації

Використовуйте `obj_tree`, `obj_rocks`, `obj_brazier`, `obj_wall`, `obj_grave`. Їхні спрайти видно в Room Editor. Декорації не впливають на маршрут чи зіткнення. За потреби створюйте нових нащадків `obj_decor`.

## Порядок запуску й fallback

У кожній кімнаті першими розміщені `obj_app` і `obj_audio`. Вони persistent і видаляють лише зайві власні дублікати. Після створення всіх екземплярів Room Creation Code викликає `wp_room_setup()`.

Bootstrap перевіряє наявність необхідних сервісів, збирає вже розміщені маркери/майданчики та додає лише відсутні обов'язкові елементи. Видалені декоративні об'єкти не повертаються. `wp_ensure_buttons()` ідемпотентна: повторний виклик не дублює кнопки.

## Час і стани

`obj_game.sim_dt` обчислюється в Begin Step. Всі рухи, атаки й ефекти читають `wp_dt()`. При паузі, опціях або результаті повертається нуль. Візуальний час UI живе окремо, тому меню залишається активним.

`global.page`: `splash`, `language`, `main`, `game`, `pause`, `options`, `text`, `confirm_new`, `result`.
`obj_game.result`: 0 — бій, 1 — перемога, 2 — поразка.

## Баланс та локалізація

Каталог `global.towers` у `scr_config` містить ціну, базову шкоду, радіус і інтервал пострілу. Масштабування покращень — `obj_tower/Step_0.gml`. Параметри ворогів — `obj_enemy/Create_0.gml`. Склад хвиль детермінований і описаний `wp_wave_list()`; preview показує той самий склад.

Для тексту використовується `wp_tr("English", "Українська")`. Шрифти містять повний український алфавіт, включно з Ґ/Є/І/Ї. Зміна мови в опціях застосовується одразу.

## Версія 1.2: нові механіки

- **Пріоритет цілі.** `obj_tower.target_mode` (0–3). Змінюється `wp_cycle_target()` (клавіша `T` в `obj_game/Step_1`, або кнопка `action="target"`). Кнопка створюється fallback-ом `wp_ensure_buttons()` лише в `rm_game`/`Room1` і не малюється, поки вежу не вибрано. Її можна перемістити в Room Editor, як і будь-яку іншу.
- **Рекорди.** `wp_record_result()` викликається з `wp_end_run()` лише при перемозі поза `rm_test`. Зберігає `global.best_stars` / `global.best_time` у settings; `obj_game.new_record` керує написом на екрані результату. Пороги зірок — `wp_rating()` у `scr_config`.
- **Спливаючі тексти.** `wp_popup(x,y,text,color)` створює `obj_effect` із `fx_kind=2`. Для тексту з прозорістю використовуйте `wp_text_a`, бо `wp_text` завжди скидає alpha до 1.
- **Банер хвилі, смуга прогресу, склад хвилі, червона рамка, підпис ядра, підказка покращення** малюються в `obj_hud/Draw_0.gml`; жодних симуляційних змін там немає.
- **Автопауза** у `obj_app/Step_1` через `window_has_focus()`; не діє з `--wp-test`.

## Збереження

Windows sandbox: `%LOCALAPPDATA%/Wall_Protocol/`.

- `wp_settings.json` — мова, гучність, fullscreen, ефекти; з 1.2 також `best_stars` та `best_time` (необов'язкові, старі файли валідні).
- `wp_save.json` — останній похід; `wp_save.bak` — попередній перевірений стан.
- `wp_save.json.tmp` — проміжний запис; неповний файл не підміняє резервну копію.
- Тести використовують лише окремий префікс `wp_test_`.

У кожної вежі з 1.2 є необов'язкове поле `mode` (пріоритет цілі); відсутнє поле означає 0. Зберігаються plain JSON-значення, без instance ID: у ворогів є стабільний `uid`, снаряди посилаються на нього. При restore зв'язки будуються заново. Валідація перевіряє версію, діапазони, масиви, унікальність ключів, відомі типи, снаряди й маршрут. Відновлення перевіряє всі майданчики та маршрут перед зміною світу.

Після зміни маршруту чи переміщення зайнятої основи старий save не завантажується; гравець повертається до меню без втрати старого файлу. Почніть новий похід. Перемога/поразка завершують активний save. Ефекти й декоративний стан не зберігаються.

## Інструменти

```powershell
python tools/check_gml.py
python tools/validate_project.py
./tools/build.ps1
./tools/test.ps1
```

`check_gml.py` не потребує GameMaker: ловить незбалансовані дужки/лапки, невизначені `wp_*`, неправильну кількість аргументів, неоголошені `_локальні` змінні, невідомі ресурси та кольори палітри. Це **не** компілятор — він не знає вбудованих функцій GML, тож Project Health в IDE усе одно обов'язковий.

`build.ps1` знаходить runtime автоматично; можна передати `-RuntimePath` і `-UserPath`.
`test.ps1` запускає готову збірку з `--wp-test` та копіює звіт/знімки до `build/verification`.

`validate_project.py` використовує локальний JSON5-парсер у `tools/vendor` і Pillow. Це інструменти розробки; вони не входять до гри. `build_fonts.py` потрібний лише для перепакування шрифтів. Звичайна робота в IDE не потребує Python.

**Не запускайте повторно `build_resources.py` або `finalize_layout.py` після власного редагування кімнат.** Це історія міграції, вона може повернути початкову розстановку. `refresh_events.py` синхронізує тільки списки подій; кімнат не змінює.
